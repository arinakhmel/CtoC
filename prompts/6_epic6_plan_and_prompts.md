## 0. Перед стартом (обов'язково)

1. На будь-якому комп'ютері чи акаунті спочатку `git checkout main && git pull`. Локальна `main` відставала від GitHub більше ніж на 100 комітів: без коду Епіків 2–5 нічого не запрацює.
2. `pnpm install`, потім `pnpm typecheck && pnpm test`. Усе має бути зеленим **до** твоїх змін, щоб потім було видно, що зламала не ти.
3. Одна історія = одна гілка = один PR у `main`, як у команди: `epic6/us-34-35`, `epic6/us-36`, `epic6/us-37-38`, `epic6/e2e`.
4. Кожну історію робити через скіл проєкту `/implement-story US-xx`: він сам читає traceability, api.md, domain-model, показує план і **чекає на твоє «так»**. Не погоджуйся наосліп, звір план із розділом 2 цього файлу.

## 2. Знайдені проблеми у вимогах і рішення, яких треба дотримуватися

Це головне місце, за яке можуть зняти бали: сценарії в `requirements.md` подекуди суперечать дизайну. Тексти історій **міняти не можна** (правило `.claude/rules/input-docs.md`). Рішення вже записані в `traceability.md` §4 і `overview.md` §7.2, їх треба дотримуватись і згадувати в коментарях до тестів (`// W-xx, decided: …`).

| # | Де | Проблема | Рішення |
|---|---|---|---|
| 1 | US-34 sc.2, sc.3 | Згадують «платіжний шлюз» і «вебхук», але оплата симульована, шлюзу й вебхука немає | **W-06 ✔**: sc.2 = штучна помилка провайдера → відкат, ескроу лишається `held`. sc.3 = повторний accept → 409 `TASK_ALREADY_DONE`, рівно один `payout`. Вже зроблено, не переробляти |
| 2 | US-35 sc.2 | «Стандартні правила округлення» не уточнено | ADR-0007: копійки цілими, `commission = round_half_up`, `net = price − commission`, тож `gross = commission + net` до копійки. Брати **лише** `splitPrice` із `@ctoc/shared`, ніякого float |
| 3 | US-35 | Звідки брати цифри розбивки | Зі **знімка комісії на задачі** (`commission_kopecks`, `net_kopecks`, зафіксовані при публікації), не з поточної ставки. Інакше після зміни ставки адміном розбивка «попливе» |
| 4 | US-36 sc.2 | «Картка закордонного банку» не перевіряється без BIN-бази | **W-13 / OQ-13**: лише 16 цифр + Luhn. У тестовому коментарі прямо написати, що закордонний банк не перевіряється |
| 5 | US-36 | Хто і як виплачує заявку, які в неї статуси: жодна історія цього не описує | **OQ-10 / A-10**: `requested → paid / rejected`, обробляє модератор на `/mod/withdrawals`. При `rejected` гроші повертаються (`withdrawal_reversal`) |
| 6 | US-36 | Безпека номера картки | Повний номер зберігається лише поки статус `requested` (CHECK у БД уже є), в API **ніколи** не повертається, тільки `cardLast4`. Не логувати тіло запиту |
| 7 | US-37 | Назва історії каже «обсягом», чек-лист каже «описом» | **W-15 / OQ-14**: показувати назву, опис, дату. Питання конфіденційності опису замовника лишається відкритим, не вирішувати мовчки |
| 8 | US-37 sc.2 | «Скасоване замовником», але після вибору виконавця замовник скасувати не може, ендпоінта скасування немає | **W-07**: перевірити через задачу в статусі `cancelled`, створену фабрикою в тесті: accept дає 409, запису немає, у профілі його немає. Ендпоінт `/api/mod/tasks/:id/resolve` (A-09) у Епік 6 **не входить**, не будувати |
| 9 | US-38 sc.2 | «Кнопки немає», а це лише UI | Перевірити і UI, і API: `POST`/`PUT /api/me/experience` → **404** (маршруту не існує) |

### Промпт 6.2: US-36 (виведення коштів на картку)

```text
/implement-story US-36

# КОНТЕКСТ
Гілка epic6/us-36. Таблиця withdrawals, kind `withdrawal` і `withdrawal_reversal` у ledger_entries і CHECK
`status = 'requested' OR card_number IS NULL` уже є в міграції init. Прочитай ADR-0007, data-model.md (withdrawals, ledger_entries),
domain-model.md (Balance, ledger entry, withdrawal; стан-машина Withdrawal), api.md (рядки /api/me/withdrawals, CARD_INVALID, INSUFFICIENT_BALANCE).

# ЗАВДАННЯ
1. POST /api/me/withdrawals { amountKopecks, cardNumber } → 201. Тільки верифікований студент (INV-02).
   Одна транзакція: умовний updateMany балансу `available >= amount` (count 0 → 422 INSUFFICIENT_BALANCE),
   створення заявки `requested`, запис ledger `withdrawal` з від'ємною сумою.
2. Картка: схема в @ctoc/shared, рівно 16 цифр (пробіли дозволено ввести, але прибрати до перевірки) + Luhn → інакше 400 CARD_INVALID.
   W-13 вирішено так: «закордонний банк» не перевіряється (немає BIN-даних), напиши це в коментарі до тесту sc.2.
3. Безпека: повний номер ніколи не повертається в жодній відповіді, лише cardLast4. Переконайся, що логер не пише тіло запиту.
4. GET /api/me/withdrawals: лише власні заявки студента, найновіші зверху.
5. UI на /me/finance: форма «Вивести кошти» (сума, номер картки) з підтвердженням, помилки за code, список заявок зі статусами українською.
6. Бонус, якщо час є (OQ-10, A-10, історії немає, тому познач як placeholder): /mod/withdrawals для модератора,
   POST /api/mod/withdrawals/:id/mark-paid і /reject (з причиною). Обидва лише `WHERE status='requested'` (повтор → 409 ALREADY_DECIDED),
   card_number очищується, при reject гроші повертаються на баланс із записом `withdrawal_reversal` у тій самій транзакції. Пиши в audit.
7. Онови api.md (тіла §4), traceability §5, і §4 для W-13.

# ТЕСТИ
- US-36 sc.1 [API]: баланс достатній, валідна картка → 201, баланс зменшився рівно на суму, один ledger `withdrawal`, у відповіді лише last4.
- US-36 sc.2 [API]: 15 цифр, 17 цифр, літери, 16 цифр без Luhn → 400 CARD_INVALID, баланс не змінився, заявки немає.
- US-36 sc.3 [API]: баланс 300 грн, вивід 500 грн → 422 INSUFFICIENT_BALANCE, нічого не змінилось.
- Гонка (testing.md §4): баланс 500 грн, два паралельні виводи по 300 → один 201, один 422, баланс 200, рівно один ledger.
- Відкат: помилка на кроці ledger → баланс не змінився, заявки немає.
- INV-20: після всіх дій баланс = сума ledger-записів власника.
- Доступ: неверифікований студент → 403 STUDENT_NOT_VERIFIED, замовник → 403 ROLE_FORBIDDEN.
- UI: помилка CARD_INVALID показана біля поля (role="alert"), кнопка неактивна під час відправки.

# ОБМЕЖЕННЯ
Ті самі, що в 6.1. Без мінімальної суми виведення, комісії за вивід чи інших правил, яких немає у вимогах.
В кінці pnpm typecheck і pnpm test зелені, вивід мені, потім /check-story US-36.
```
