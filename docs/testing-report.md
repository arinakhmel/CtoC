# CtoC: звіт про тестування (US-02, US-03, US-04)

Гілка `practice-6`. Стратегія: [`testing-strategy.md`](testing-strategy.md). Усі промпти й текст скіла: [`prompts/all-prompts.md`](prompts/all-prompts.md). Усі перевірки однією командою: `pnpm test:all` (скрипт у кореневому `package.json`, раніше цей ланцюжок `pnpm typecheck && pnpm test && pnpm test:e2e` набирали вручну; див. розділ 5).

## 1. Покриття автотестами

Назви тестів мають вигляд `US-xx sc.N …`, їх можна запустити окремо: `pnpm --filter @ctoc/web exec vitest run -t "US-02"` (для API: `@ctoc/api`).

### US-02 «Як це працює» (`apps/web/tests/how-it-works.test.tsx`, 16 тестів)

| Сценарій | Що перевіряє тест |
|---|---|
| sc.1 Happy Path | Один нумерований список `<ol>` із 3–4 кроків; іконка прихована від читача з екрана (`aria-hidden`), є заголовок і опис; типові кроки не порожні; 3 і 4 кроки від викликача показуються як є |
| sc.2 Edge Case: кількість кроків | 0, 1, 2, 5, 8 кроків дають типові кроки, `null` або відсутній список теж |
| sc.3 Edge Case: порожній опис | Порожній або пробільний опис відомого кроку замінюється шаблонним; крок без шаблону ховається; якщо після приховування лишилося менше 3, показуються типові; у списку немає порожніх елементів; текст на кшталт розмітки показується як текст |

### US-03 Комісія (`apps/api/tests/settings/settings.test.ts`, `apps/web/tests/settings.test.tsx`)

| Сценарій | Що перевіряє тест |
|---|---|
| sc.1 Happy Path | `GET /api/public/settings` без сесії: 200, ціле число в базисних пунктах, `Cache-Control: no-store`; тіло містить лише ставку; на `/terms` відвідувач бачить цифри (`10%`, `12,5%`, `0%`) |
| sc.2 Edge Case: комісія недоступна | Помилка сервера або мережі: на `/terms` є `role="alert"`, вигаданого числа немає; після помилки є кнопка «Спробувати ще раз» |
| sc.3 Edge Case: адміністратор змінює ставку | `PUT /api/mod/settings`: наступний публічний `GET` показує нове значення; `Cache-Control: no-store` на `PUT` і `GET` модератора (додано в цій роботі); значення поза діапазоном (`-1`, `5001`, `10.5`, `'1000'`, `null`) і порожнє тіло дають `400 VALIDATION_FAILED`, нічого не змінюється; студент і замовник отримують `403 ROLE_FORBIDDEN`, без сесії `401`, чужий Origin `403 ORIGIN_MISMATCH`; завдання, опубліковане до зміни, зберігає стару ставку |

## 3. Знайдені дефекти

Виправлені в коміті `e480b70`; тести проти старого коду падають, з виправленням проходять.

1. **Немає способу повторити після помилки** (`TermsPage.tsx`, `SettingsPage.tsx`). Повідомлення «Спробуйте ще раз» не мало кнопки. Виправлення: кнопка «Спробувати ще раз», яка перезапитує ставку і вимикається під час запиту. Тести: `US-03 sc.2 after an error the visitor can ask again…`, `US-03 sc.3 if the stored rate cannot be read the moderator can try again`.
2. **Застарілий стан форми модератора** (`SettingsPage.tsx`). Після збереження «Збережено: 12%» і помилка сервера лишалися на екрані, коли поле вже редагувалося. Виправлення: нова правка поля скидає підтвердження і помилку мутації. Тести: `…editing the field removes the old «Збережено» confirmation`, `…removes the old server error`.
3. **Прогалина покриття US-03** (не дефект коду). Не було перевірки `Cache-Control: no-store` для `PUT` і `GET /api/mod/settings`. Додано тест `US-03 sc.3 the moderator answers PUT and GET … no-store`. Через спільне встановлення заголовка в `app.ts` цей тест не ловить видалення рядка з одного маршруту (див. спробу 1).

## 4. Інженерна рефлексія

Це оцінка ШІ щодо власної роботи в цій сесії, лише факти, які я бачу.

- **Прогалина в перевірці ключових слів.** Слова «резервування» і «виплата на картку» перевірялися тільки побічно, через заголовки етапів. Явної перевірки тексту сторінки не було. Додав тест, що шукає обидві фрази в тексті без урахування регістру.
- **Невдалий вибір мутації.** Для «зламай код» я першим взяв рядок `no-store` у маршруті, не перевіривши, що той самий заголовок ставить `app.ts`. Тест правильно лишився зеленим, а мутація була безглуздою. Замість цього перевірив умову мінімуму кроків. Висновок: перед мутацією треба перевіряти, чи вона змінює спостережувану поведінку.
- **Помилка в новому тесті.** Мій тест «правка поля прибирає помилку» набирав `1` після `10`, що дає `101`, понад ліміт, і спрацьовувала валідація. Тест упав за моєю помилкою, а не через код. Виправив на очищення поля і ввід `15`.
- **Хибні припущення про довкілля.** Спершу взявся писати тести для US-02 і US-04, не перевіривши, що самих сторінок ще немає (були лише заглушки), і не знайшов готових гілок. Після питання з'ясувалося, що реалізація вже є в `feature/us-02` і `feature/us-04`.
- **Ізоляція в стратегії.** Припущення «неточність з ізоляцією в `testing-strategy.md`» у цій сесії я не перевіряв і не виявляв, тому не заявляю про нього. Одне спостереження: e2e-база `e2e.db` між запусками не очищується (описано в стратегії), тож дані накопичуються, але імена унікальні за запуск.
- **Ненадійний прогін.** Один спільний `pnpm test` перервався падінням воркера API (`ERR_IPC_CHANNEL_CLOSED`); повторний прогін пройшов. Причину я не досліджував, тож це може повторитися.
- **Чого не зроблено.** Ручний smoke не проходився; e2e виконано лише в Chrome (не в Chromium із Playwright); `architecture-reviewer` і `/check-story` не запускалися, тому Definition of Done з CLAUDE.md не закрито повністю.

## 5. Зміни в запуску тестів

- У кореневий `package.json` додано скрипт `"test:all": "pnpm typecheck && pnpm test && pnpm test:e2e"`. Раніше його не було: три команди запускали окремо.
- Команду `pnpm test:all` вказано в `README.md` (таблиця команд і рядок про єдину команду) і в `docs/testing-strategy.md`.
- Ланцюжок зупиняється на першому кроку, що впав (`&&`): якщо `typecheck` або `test` червоні, e2e не запускається.
- `pnpm test:all` на цьому коміті ще не запускався повністю; його складові виконувалися окремо (розділ 1). Для e2e потрібен встановлений Chromium (`pnpm exec playwright install chromium`).
